- 確認役が調べたこと:アップデートの仕組み(`src/app/updater.ts`)は PU-10f から変わっていない。作られる Service Worker には SKIP_WAITING を受ける仕組みがある(`dist/sw.js`)。公開(`.github/workflows/deploy.yml`)は main への push のたびに走る。13:55 にルビーの T2-18a の公開が終わり、13:58〜13:59 に確認役の仕様書だけの push で、もう一度公開が走っていた。**見立て**:待っている版(13:55)に切り替えている最中に、さらに新しい版(13:58)が入り、待っていた版が捨てられて(redundant)、5 秒以内に切り替わらなかった。時刻の一致による見立てで、確定ではない。
- 前提:PU-18。
- 進め方:**2つのコミット**(PU-19a:公開の条件、PU-19b:やり直し)。PU-19b はテストを先に書く。version を patch で上げる。

## PU-19b:切り替えに失敗したら、1回だけやり直す

- `applyUpdate` で、5 秒たっても切り替わらなかったとき、**待っていた版が捨てられていた(`state === 'redundant'`)か、registration に別の待っている版(`reg.waiting`)・入れている途中の版(`reg.installing`)があるとき**は、その新しい版を見つけ直して(入れている途中なら入れ終わるのを待って)、**もう1回だけ**切り替えを試す。それでも失敗したら、今の案内(「切り替えられませんでした…」)を出す。
- 切り替えの途中で `statechange` が 'redundant' になったら、5 秒を待たずにやり直しへ進む。
- テスト(偽の Service Worker):待っていた版が途中で redundant になり、新しい版が waiting に入る → 新しい版に SKIP_WAITING を送って読み込み直す/やり直しも失敗 → false(案内)/やり直しは1回だけ。
