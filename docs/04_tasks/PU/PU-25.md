# PU-25 アップデートの切り替え:合図を受けても新しい版が動き出さないときに、自分で読み込み直す

- 目的:管理者の実機確認(2026-10-09 12:27・12:28、Fold 8、「アップデートの記録」の写真、会話)。「アップデートする」で2回とも「切り替えられませんでした」。
- 記録で分かったこと(確認役):
  - 2回とも、押した時点で `待っている版=installed / active=activated / waiting=installed / controller=あり`。SKIP_WAITING を2回送っても、15 秒後まで `installed` のまま。`activating` にもならない。
  - 公開の直後ではない(最後の公開は 10:05 ごろに終わっている)。PU-19 の「公開と重なる」説は当たらない。
  - ビルドした `sw.js` には、SKIP_WAITING を受けて `self.skipWaiting()` を呼ぶ処理がある。10:04 には同じ流れで切り替わっている。
- 考えられる原因:
  - Chrome は、skipWaiting のあとも、**今動いている版がまだ仕事を抱えている間は、新しい版を動かし始めない**(仕事が終わるか、長い待ち時間が過ぎるまで `installed` のまま)。
  - 何時間も開いたままの画面では、こうなりやすいと考える。
  - 合図そのものが届いていない可能性も残る。どちらかを確かめるため、記録を増やす。
- 進め方:1つのコミット+報告。テストを先に書き、RED を確かめてから直す。version を patch で上げる(main より大きく、package-lock もそろえる)。「PU-25 の報告」を push して止まる。

## 決まり

1. **15 秒たっても `installed` のまま(今の「あきらめた」の場面)のときは、案内を出す代わりに、画面を1回だけ読み込み直す。**
   - SKIP_WAITING を送ったあとなので、読み込み直しで今の画面の仕事が片付けば、新しい版が動き出す。
   - 読み込み直す前に、`localStorage` に「切り替えのために読み込み直した」印(`seikei-update-retry`。時刻と、待っていた版の `scriptURL`)を置く。記録の結果は `'retry-reload'` として、`読み込み直した(切り替えのやり直し)` と書く。
2. **起動したとき**(`main.ts` から `recordStartup()` を1回呼ぶ)に、印があれば、記録の一番新しい回に次の1行を足して、印を消す。
   - 足す1行:`起動した: 版=__APP_VERSION__ / active=… / waiting=… / installing=… / controller=…`
   - それでもまだ `waiting` があるとき(切り替わらなかったとき)は、設定画面の案内に「切り替えられませんでした。アプリを閉じて、もう一度開いてください」を出す。今と同じ文で、起動のあとに設定画面を開いたときに出す。
   - **読み込み直しは、印がある間は2度としない**(読み込み直しがくり返されないため)。
   - 印が 10 分より古ければ、無いものとして消す。
3. **合図が届いたかを確かめる記録**:SKIP_WAITING を送るときに `MessageChannel` の口を添える。
   - 届いた返事が来たら `返事があった` と記録する。今の `sw.js` は返事をしないので、記録に出ないのが普通。
   - `sw.js` を作り替える必要はない。返事の仕組みは今回は作らない。記録の場所だけ用意する。
   - **この項は省いてよい。** その場合は報告にそう書く。
4. 5 秒の時点で `activating` のときと、`redundant` で見つけ直すときの流れは今のまま。

## テスト(先に書く)

- 15 秒たっても `installed` のまま:案内を出さずに、読み込み直しが1回呼ばれる。印が置かれ、記録の結果が `'retry-reload'` になる。
- 印があるときに、同じ失敗がまた起きた:読み込み直さず `false` を返す(今の案内)。
- `recordStartup`:印があれば記録に「起動した」の行が足され、印が消える。印が無い・10 分より古いときは何も足さない。
- 今ある、切り替えに成功するテスト(controllerchange・activated・activating の延長・redundant の見つけ直し)は、そのまま通る。
